# @skillcdn/db

PostgreSQL schema, migrations and the query layer. PostgreSQL is the only stateful dependency of the product ([ADR-0004](../../docs/adr/0004-postgresql-only-state.md)).

**Status:** the schema for serving repositories: repositories, the names that are none, ref cache, per-commit index with full-text search, a content-addressed body store, daily usage counters, the operator's content, and what signing in needs: users, their credentials and sessions, OAuth clients, codes, grants and tokens, the tokens people make for agents, and the permission cache; where the server has the `vector` extension, the vectors of the search by meaning, with how far each snapshot has been embedded; and the job queue, in a schema of its own ([ADR-0064](../../docs/adr/0064-meaning-search-runs-on-pgvector-and-pg-boss-behind-an-embedder-port.md)).

## Layout

```
src/
  schema.ts      Drizzle table definitions (one file: drizzle-kit reads it directly)
  client.ts      pool construction from a connection string passed in by the caller
  migrate.ts     applies migrations and installs the job queue's schema; reports whether the schema is current
  jobs.ts        the job queue (pg-boss) in its own schema: queues, jobs, schedules and counts, for the roles
  queries/       typed query functions, the only public way to reach the data
  testing.ts     per-file throwaway databases for integration tests (`@skillcdn/db/testing`)
migrations/      generated SQL, committed, shipped inside the package
```

Other workspaces hold an opaque `Database` and call the exported functions. They never see the ORM or SQL.

## Working on the schema

```sh
docker compose -f deploy/compose.dev.yaml up -d      # PostgreSQL 18 with the vector extension, on 127.0.0.1:5432
# edit src/schema.ts, then:
pnpm --filter @skillcdn/db run generate --name <what-changed>
# review the SQL in migrations/, run the tests, commit schema and migration together
```

Integration tests (`*.int.test.ts`) create a database per test file, apply the real migrations and drop it afterwards. They connect to the compose database unless `TEST_DATABASE_URL` points elsewhere, and they fail, not skip, when no server answers.

## Data model

Index entry front-matter also stores resolved local Markdown references (`href` and repository-root `path`), `linkedOnly` for files made readable by links without entering the document catalog or search, and `manifestError` for repository manifests whose presence defines a closed boundary despite an unreadable body. These are optional JSON fields; they do not add database columns.

Primary keys are `uuid DEFAULT uuidv7()` and timestamps are `timestamptz`, with one exception noted below. Tenant-scoped tables carry `account_id`, and every query on them takes the account.

| `repos` | A repository, identified by the host's immutable id, so renames and transfers keep their index; `host` is a git host, or `local` for a pack served from a directory of the deployment, whose id is its `owner/name` ([ADR-0071](../../docs/adr/0071-a-deployment-serves-packs-from-a-directory-of-its-own.md)). Holds what the host last reported: name, default branch, description, visibility. | `repo_aliases` | An `owner/name` spelling from an address (lowercase) and the repository it currently names, with `checked_at` for the freshness of that fact. A lookup index read before the account is known, so it is not tenant-scoped. | unique `(host, owner, name)`; `repo_id` |

Only requests from nobody in particular write it, so a row says the same about a private repository as about a name that is nothing. Nothing in a row identifies a client. `client` is the number of distinct clients, written when the day is folded. | unique `(repo_id, day, metric, subject)`; `(day, metric)`; `account_id` |
| `usage_clients` | The distinct clients seen at a public repository on the day being counted: `client` is an HMAC of the client's address under the key of that day, which is derived from the deployment's secret and the day and stored nowhere. Text is derived from the bytes on read. How it behaves:

- **Claiming a snapshot** is one atomic `UPDATE`: it succeeds for a `pending` row, for an `indexing` row whose lease expired, and for a `failed` row whose `retry_at` has passed. Exactly one process wins, and its claim carries an owner token. Renewing, writing, failing and releasing succeed only for the holder, so a process whose lease ran out while it was paused cannot undo what its successor did. The winner renews its lease while it works and releases the row on shutdown.
- **Writing an index** replaces the entries and marks the snapshot `ready` in one transaction, so readers see no index or a complete one. It refuses when the caller no longer holds the snapshot.
- **Publication metadata** in `front_matter` records manifest `exclude` paths and `overviewOnly` README introductions. Exclusions and unreadable policies close their scopes before indexing descendants. Overview-only entries remain readable without search vectors or document counts; manifest lookup also requires a visible entry.
- **Search vector**: built by the indexer with the word rules of `@skillcdn/core`, in the text form of a `tsvector`, and stored with a cast and nothing else (ADR-0063): weight A for the original skill name and document title, B for the original description, C for the words of the path, D for the parsed body, its first 200,000 characters and up to the bytes a `tsvector` holds (1 MB of lexemes and positions, which a long text read by pairs of characters reaches first), read with the stemmer the pack's `language` names and by pairs of characters in the scripts without word stems. Markdown front-matter is excluded from body search, so display translations do not become search aliases. No text-search configuration of the server is involved: the same vector is what the `skillcdn` command keeps in memory, so a pack is found by the same words wherever its index is kept.
- **Search** takes the lexemes of a query, as `queryLexemes` reads it with the pack's rules, as a `tsquery` of alternatives: any of them may match, `ts_rank` orders, with skills boosted over plain documents, and `rankSearchVector` in memory computes the same rank; `search-parity.int.test.ts` holds the two against each other. No lexemes return nothing. The mount path is matched with `starts_with`, so `%` and `_` in a path are ordinary characters. Result order uses the `C` collation and is the same on every database.
- **Usage counters** are written with an upsert that adds, so every process reports what it counted without knowing about the others; the deployment's own counters (`addServiceUsage`) the same way. **Distinct clients** are rows of `usage_clients` inserted with "do nothing" on conflict; `foldUsageClients` moves every day before the given one into `client` counts and deletes the rows in the same statement, so processes that fold at once each move their own share and the totals still add up. The deployment's rows (`addServiceUsageClients`) take the app a client is later seen with when they were written without one, and `foldServiceUsageClients` moves them into `client` and `client_app` counts the same way. `getRepoUsage` is scoped to an account like everything else. `listTopRepositories` and `listTopSubjects` deliberately are not: they are what a public ranking is made of, and the rule that keeps them safe is in the query itself, which reads only repositories that are public right now. A repository that goes private drops out of them with all its history. `getServiceUsage` reads the deployment's totals, which name nothing.
- **Section vectors** are written per body under one key (`writeSectionVectors`): what is there stays, since the same bytes under the same model and rules give the same vector, and `blobsWithoutVectors` says which bodies have nothing under the key yet. `searchSectionVectors` is the exact nearest-neighbor search of ADR-0064: every section of the mount's searchable entries that has a vector under the key is compared with the query by cosine distance, with no approximate index, since a mount has thousands of sections at most; best first, ties by path and section, so that the order is the same on every database. The column names no dimensions, so one table serves every model, and the row's `dimensions` with the check keep each vector the size of its key; a query of other dimensions is refused before it is sent. Purging a repository drops the vectors of the bodies no entry names any more, with the bodies.
- **Snapshot embeddings** record the worker's progress per snapshot and key: `recordSnapshotEmbedding` adds a slice's counts and marks the row complete when the slice says so, and a completion is never undone by a later slice. `listSnapshotsToEmbed` is the backfill: the ready snapshots some cached ref points at, without a complete row under the key, of the repositories the worker embeds unasked, ranked ([ADR-0072](../../docs/adr/0072-the-worker-embeds-the-packs-first-and-the-rest-when-asked.md)): the operator's listed repositories, given as `/gh/owner/repo`, and the packs of the deployment's directory first, then the snapshots with a manifest and the private repositories, then those with a skill, each rank newest index first, and never a repository that is none of these; after a change of model that is every served pack, of public repositories alone when asked. `tierOfSnapshot` asks the same rank of one snapshot, for whatever queues or runs its embedding. `embeddedBytesOfRepository` sums a repository's bytes over its snapshots under the key, for the bound per repository; `getRepo` reads a repository by its id, with what the host reported, for whoever decides about it. `deleteEmbeddingsOutsideKey` drops the vectors and the records of every other key, in batches, for once nothing is left to embed under the new one (ADR-0065).
- A transferred repository moves to its new account; snapshots written under the old account are no longer visible and the repository is indexed again.
- **Refresh tokens rotate under a row lock**: `rotateOAuthRefresh` selects the pair `for update`, so two exchanges of one token see each other. The first marks it rotated and inserts the next pair; another within the caller's grace gets a pair of its own; one after it deletes the grant, and the tokens with it. A grant keeps only its newest pairs, as many as the caller says, and a user only their most recently used grants (`createOAuthGrant`): what a signed-in person can insert is bounded. `countUnusedOAuthClients` lets the caller bound the clients nobody has used, which anyone can insert.
- **What a user may read under a name** (`findReadableRepo`) is one query from the user's side, alias and permission joined: it finds nothing for a name that is nothing and for a repository the user was never let see alike.
- **Forgetting a user's access** (`forgetUserAccess`) deletes their sessions, codes, grants, tokens and remembered answers together: what stands on a credential goes when the credential does.
- **The indexed repositories of an account** (`listIndexedRepositories`) are read by the host's immutable account id: public as last recorded, default branch indexed, with skills a mount of the root would count, most skills first. The caller confirms with the host that each is still public before showing it to everyone.
- **Expired rows** are removed by the caller's sweep (`deleteExpiredSessions`, `deleteExpiredOAuth`, `deleteExpiredRepoTokens`, `deleteStaleRepoPermissions`, `deleteStaleMissingRepos`, `deleteUnusedOAuthClients`); every read checks the time itself, so the sweep only keeps the tables small.

**The job queue** (`jobs.ts`) is pg-boss in the schema `pgboss`, which `migrateDatabase` installs and brings to the library's version after the migrations above, so that the `migrate` role creates it and the `api` and `worker` roles use it without migrating (ADR-0064). `createJobQueue` opens it on the pool of a `Database`: every queue is made sure of with its settings at start (`ensureQueue`: how often a failed job is tried again, with a backoff that doubles, and how long one attempt may run), a job is queued with a priority and a singleton key of which at most one job is queued and one is running at a time (`send` says when the key kept it out), a worker runs the jobs of a queue one at a time per slot in priority order and, among equals, oldest first (`work`), a job may run on a cron schedule under a key (`schedule`), the jobs that wait are listed (`waiting`) and one of them given another priority in place, never one that runs (`reorder`), and the counts of a queue are read fresh (`counts`). The `worker` role also runs the queue's own maintenance and its schedules; the `api` role only sends. What the queues are named and what their jobs carry is the server's to say. The git host's events need no table of their own: they end rows of the tables above (`expireRepoRefs`, `expireRepoAliases`, `deleteRepoPermissionsOf`, `purgeRepositoryIndex`).
