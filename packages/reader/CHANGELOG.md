# @skillcdn/reader

## 0.4.0

### Minor Changes

- [`a9da901`](https://github.com/skillcdn/skillcdn/commit/a9da901f2a4a6b0f28a5e590e2214b8d700bb710) Thanks [@samo-lucid](https://github.com/samo-lucid)! - Breaking: packs of documents are served through their structure and their words (ADR-0063, phase A).
  
  - A search result names the sections of a document that matched: the heading path, the `offset` and `limit` that read the section with `read_repo_file`, and an excerpt, left out when it only repeats the document's summary. `FindItem` documents carry `sections`; the REST `find` body carries them as `sections` with a nullable `excerpt`.
  - `browse_repo` given a file path answers the file's outline: every heading with its level, text, offset and the length of its section, paged. `BrowseResult` carries `outline` (`FileOutline`) and the REST `browse` body carries `outline`.
  - The word rules read the scripts without word stems (Han, Hangul, Hiragana, Katakana) by pairs of characters, and a pack's `language` chooses the stemmer, English being the only one at present: `searchLexemes`, `queryLexemes` and `searchVectorOf` take a language, and `wordRulesOf` names the rules.
  - The search vector is built by the indexer and stored as it is: `IndexEntry.search` holds it in the text form of a PostgreSQL `tsvector` (`serializeSearchVector`, `parseSearchVector`, `serializeSearchQuery`), and `IndexEntry.searchBody` is gone. `IndexStore.search` takes the lexemes of a query instead of the query. The reading rules are version 11, so a deployment rebuilds the indexes it holds when they are next asked for.
  - New in `@skillcdn/core`: `outlineMarkdown`, `headingPaths`, `matchSections`, and the result types and REST schemas of sections and outlines.
  - The `skillcdn` command outlines a file with `browse <pack> <file>`, prints the sections a search matched, and `check` prints how many sections each document has.

### Patch Changes

- [`95c13d0`](https://github.com/skillcdn/skillcdn/commit/95c13d0229f5102de02e201b43a498bb8a4e8f76) Thanks [@samo-lucid](https://github.com/samo-lucid)! - A page of a file lists the links within it, not the first links of the whole file: a section read by its offset and limit is no longer followed by references to other parts of the document. A page that delivered the length it was asked for says where the file continues ("The file continues at offset N.") instead of telling the reader that more follows, since a section read is complete at its end; "More follows" is kept for a page the response budget cut short of what was asked. The file result carries the requested length as requestedLength for the renderer to tell the two apart.

- [`daabd7f`](https://github.com/skillcdn/skillcdn/commit/daabd7fbba1feba480f07f8be7262c1825c64980) Thanks [@samo-lucid](https://github.com/samo-lucid)! - `createMemoryIndex` takes `vectors`, the vectors of the sections of each body by its blob hash (`MemoryVectors`, `MemorySectionVector`), and its index then answers `searchByMeaning` over them, exactly, as a deployment's database answers one (ADR-0064): a `Reader` given an embedder searches a directory by words and meaning. Left out, the words answer alone, as before.

- [`5f1c0fc`](https://github.com/skillcdn/skillcdn/commit/5f1c0fc271d72807f45944fc45cb32f810e67a9a) Thanks [@samo-lucid](https://github.com/samo-lucid)! - A mount of a private repository carries no provenance notice (ADR-0061): the notice follows a public repository nobody vouched for, and nothing else. `MountSummary` and the reader's `MountContext` take an optional `visibility`, read as `public` when absent, and the results read from the REST API take it from the repository's `visibility`. A directory served by the command is private and verified, as before, so nothing changes for it.

- [`0e2052c`](https://github.com/skillcdn/skillcdn/commit/0e2052c306625d0ebe75513c5e0ada3b4e23e5b5) Thanks [@samo-lucid](https://github.com/samo-lucid)! - A reader may be handed an index served in place of the one of the mount's own commit, while that one is being built or could not be: the `index` dependency's ready outcome takes a `substitute`, the commit the index was built from and the ref's `newest` commit with why it is not served. Every result then names the commit it was read from, the `Source` line of a tool result carries one clause more (`newest <commit> indexing`, `newest <commit> failed (<code>)`, or `being reindexed` for the same commit under newer reading rules), the connection instructions say so in one sentence, and the `mounts` route answers `newest` beside `commit` (`null` while the two are the same). The page the skills extension lists from such an index is kept as briefly as an empty one, so that the client asks again soon. A caller that hands over no substitute sees nothing new.

- [`57f0ad6`](https://github.com/skillcdn/skillcdn/commit/57f0ad6aa0ab3c6f4fd092d6923d7650367a9e6e) Thanks [@samo-lucid](https://github.com/samo-lucid)! - Each word of a query weighs by its rarity among the entries searched: a code, a number or a name that few documents hold decides the order, a word every document repeats decides next to nothing, and the sections of a document are ranked with the same weights. `rankSearchVector` and `matchSections` take the weights, `queryWeights` makes them from how many entries hold each word, and the `IndexStore` port gains `frequencies(path, lexemes)`, which the memory index answers; a store that does not count leaves it out and ranks as before. A match in a name now counts twice a match in the body, no more (`SEARCH_WEIGHTS` 1.0, 0.85, 0.7, 0.5 for the name, the description, the path and the body). A hyphenated code with a digit part, or across scripts (`OIW-PV-120`, `6635-81-302-5518`, `서돌-4`), is a word of the search vector beside its parts, so that the code finds the one document that holds it; the reading rules are at version 12 for it, and a deployment rebuilds its indexes as they are next asked for.

- [`95c13d0`](https://github.com/skillcdn/skillcdn/commit/95c13d0229f5102de02e201b43a498bb8a4e8f76) Thanks [@samo-lucid](https://github.com/samo-lucid)! - Over MCP, the outline of a file comes in pages that fill the response budget, up to the 1,000 headings an outline keeps, instead of twenty headings a page: a file of a thousand headings took fifty calls to outline. A limit named by the call still bounds the page, and the REST API pages by its limit as before. The reader's browse takes the most headings of an outline page as headings, beside limit.

- [`4f63a73`](https://github.com/skillcdn/skillcdn/commit/4f63a73adf5a3afdbbe9ae1dfe7ef6e4b7dd39d3) Thanks [@samo-lucid](https://github.com/samo-lucid)! - `Reader.catalog` and `Reader.overview` say how the mount is searched (`search`: whether the vectors of its index take part, and how far its embedding has come) where the reader has an embedder and the store searches by meaning; the connection instructions follow. An index in memory given `vectors` counts its embedding, so that a directory served by the command says the same.

- [`966a1b4`](https://github.com/skillcdn/skillcdn/commit/966a1b4222021aa217864bbedbe10fafa7c909be) Thanks [@samo-lucid](https://github.com/samo-lucid)! - A search fuses the results of the words with the sections nearest in meaning, where the index keeps the vectors of its sections and an embedder is at hand (ADR-0064, ADR-0065): the `IndexStore` port gains an optional `searchByMeaning`, answering `MeaningMatch`es, and `ReaderDependencies` an optional `meaning`, with the embedder that embeds a query and a reranker that scores the first results before the page is cut. The two lists become one order by reciprocal rank fusion (`fuseRanks`, `RRF_K` in core), with the skill boost and the path order kept, and a document's sections the same way, a section found by meaning alone excerpted by `sectionExcerpt`. An embedder or a reranker that does not answer leaves the words to answer alone, and the result says how it was ranked: `FindResult.ranking`, one line in the rendered text and a `ranking` field in the REST body, present only where the search by meaning is at hand. Nothing changes for an index without vectors, such as the command's.

## 0.3.0

### Minor Changes

- [`7dabd75`](https://github.com/skillcdn/skillcdn/commit/7dabd75d1877812c8110700481ab871566df0909) Thanks [@samo-lucid](https://github.com/samo-lucid)! - The `skillcdn` command reads a pack as an agent gets it over MCP, from a directory on this machine (ADR-0055): `skillcdn skills <directory>` prints what a client is told on connect and every skill and document, `browse`, `find`, `skill` and `file` print what `browse_repo`, `search_repo`, `load_skill` and `read_repo_file` give a model, rendered by the same functions with the reads named as the commands, or the JSON of the REST API with `--json`. A skill is printed whole. The directory is addressed as `local/<its parent>/<its name>`, or as `--as` says, and is verified. `@skillcdn/indexer` exports `readDirectory`, which reads a directory as the indexer reads a commit and which `check` now reads through; `@skillcdn/reader` exports `createMemoryIndex`, an index kept in memory and searched with the word rules of `@skillcdn/core`; the renderers of `@skillcdn/core` take `ToolWords`, the names of the four reads, with `MCP_TOOL_WORDS` as their default.

- [`5a009f1`](https://github.com/skillcdn/skillcdn/commit/5a009f13e65baaed5c619d4c120d61f51d54bd38) Thanks [@samo-lucid](https://github.com/samo-lucid)! - The reads of a mount are a package, `@skillcdn/reader`, over the `IndexStore` port that `@skillcdn/core` now defines (`IndexStore`, `ReadableIndex`, `IndexOutcome`), so that the same reads answer from an index wherever it is kept (ADR-0054). `Reader` takes a `MountContext` and the index the caller answers, and gives the results the MCP tools and the REST bodies are written from: `catalog`, `overview`, `browse`, `find`, `skill`, `file`, and the skills extension's `listSkills`, `getSkill`, `readResource` and `readDirectory`.
