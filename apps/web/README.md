# @skillcdn/web

The web UI: a landing page and an explorer that shows what an agent gets from an address. English and Korean. Vite, React and plain CSS; the build is static files, prerendered once per language ([ADR-0009](../../docs/adr/0009-web-ui-prerendered-per-language.md)), plus a module the server uses to render the page of an address with its data ([ADR-0011](../../docs/adr/0011-address-pages-rendered-on-the-server.md)).

It is optional. A deployment without it is still a complete MCP and REST server for public repositories, and the UI uses nothing but the [REST API](../../docs/specs/rest.md). Signing in is the one thing that needs it: where people sign in and where they allow an app are pages.

It is published as [`@skillcdn/web`](https://www.npmjs.com/package/@skillcdn/web), with the command that builds it, so that an installation builds the pages with screens of its own from a version of them ([ADR-0101](../../docs/adr/0101-the-web-ui-is-published-as-a-package-that-builds-the-pages-with-an-installations-own.md)).

## Build it with pages of your own

In a directory of your own, with Node.js 24, take the version of the package that the deployment's image is:

```sh
npm install @skillcdn/web@<release> vite @vitejs/plugin-react
npx skillcdn-web build --config site.config.tsx --out web
```

`site.config.tsx` names the pages ([below](#pages-of-an-installations-own)), and `web` is then the product's pages with yours among them, for the server's `WEB_ROOT` ([deploy](../../deploy/README.md#a-ui-with-pages-of-your-own)). The output directory is emptied first, so the command refuses one that holds anything but a build. `npx skillcdn-web dev --config site.config.tsx` serves the pages while you write yours, against fixtures, or against a deployment with `--api https://skills.example.com`.

- **What the package carries:** the sources of the pages and the steps of their build, the documentation of its release, which the pages publish under `/docs`, the [license](../../LICENSE.md), the [trademark policy](../../TRADEMARKS.md) and the [third-party notices](../../THIRD-PARTY-NOTICES.md). Vite and its React plugin build the pages and are installed beside it.
- **Types:** a configuration imports `defineSite` and the types of what a page is given from `@skillcdn/web`. Add `"types": ["vite/client"]` to the `tsconfig.json` of the directory for the CSS modules of your pages.
- **The marks:** the pages show the SkillCDN name, symbol and wordmark where they always do, and a build made with the package may keep them as the UI of your deployment. They stay KDX Labs' marks: your own pages may not use them for anything of yours ([trademark policy](../../TRADEMARKS.md)).
- **One release:** the pages and the server change together. Build again with the package of the release you move to.

## Run it

You need git and [pnpm](https://pnpm.io/installation) (`winget install pnpm.pnpm` on Windows, `brew install pnpm` on macOS). pnpm fetches the right Node.js by itself. No container runtime, no database, no server and no token are involved.

```sh
git clone https://github.com/skillcdn/skillcdn.git
cd skillcdn
pnpm install
pnpm dev:web          # http://localhost:11189
```

The development server answers the REST API from fixtures (`dev/fixtures.ts`), so every page works and every state can be reached:

- **<http://localhost:11189/dev/states>** lists every state of every page (loading, indexing, empty, errors, long texts, a partial index) and shows every building block on one page.
- The same page has a link that signs you in as the fixture person, at once, since there is no git host to ask; the button in the sign-in dialog does the same. Signed in, the header has the account menu, `/gh/acme/private-skills` opens, and the account pages and the consent page have something to show; sign out from the menu. The fixture server knows one person and keeps that state for everyone until it restarts.
- The fixtures' deployment has a console, so the console section of the front page links one, at an example address; `SKILLCDN_CONSOLE_URL` in `apps/web/.env.local` names a real one to click through to.
- The development server writes into the page the links a deployment with terms and a privacy policy has, so the footer and the sentence under the sign-in button show both.
- Add `?lang=ko` to any URL to force Korean; that is then your preference, like a click in the language switcher, until you pick another. Without a parameter the page is shown in that preference, else your browser's language, and the URL stays as it is. Links inside the app never carry the parameter.
- Add `?country=DE` to any URL to see the page as a fresh visitor from that country sees analytics ([ADR-0051](../../docs/adr/0051-analytics-ask-first-only-where-the-visitors-region-asks-and-run-elsewhere.md)): a country that asks first (the European Economic Area, the United Kingdom and Switzerland, as the server lists them by default) shows the consent card; any other, `?country=KR` say, runs analytics at once, and the footer's "Cookie settings" opens the same card to turn them off and on. `&gpc=1` is a browser that signals Global Privacy Control: never asked, nothing to choose. What would go to analytics is logged in the browser console. Without the parameter the page has no analytics, as a deployment without an id.

To look at real repositories instead, the UI can run in front of a real server, which answers the REST API and MCP while the pages stay local: `pnpm dev:web:live` uses the hosted service at `https://skillcdn.ai`, and `pnpm dev:web:api` a server on this machine (see [`apps/server`](../server/README.md), `http://127.0.0.1:11188`). Either takes another server from `SKILLCDN_API_URL` in `apps/web/.env.local`. Fixtures remain the way to see every state, since a real server only shows the states its repositories are in. In these modes signing in belongs to that server: its routes are passed through, and the git host sends the browser back to the server's own `PUBLIC_URL`, not to the development UI.

The integrated server's default port is **11188**. To serve the built UI there as well, build the web workspace and point `WEB_ROOT` at `apps/web/dist` when starting the server. The separate Vite development UI uses **11189**, the next port up, and may choose a higher available one when that is occupied; it does not change the API port.

Replace the files, or restyle `src/pages/og-card.tsx` and take new screenshots of `/dev/og?lang=en` and `/dev/og?lang=ko` in a 1200 x 630 window (a headless browser with `--screenshot` and `--window-size=1200,630` does; force the language, since the page otherwise follows the browser's). ## Repository explorer

The overview uses `browse` to show one folder at a time, in three groups: the folders in it (each with the name its manifest gives it, its description, and what it holds), the skills (title and description in the visitor's language where the overview lists a translation, the license as the index resolved it, and whether the skill is only described), and the documents. A folder name is shown once: as the title when the folder has no other name, in the code face beside the name when it has. `?path=marketing` selects a folder within the existing connection; breadcrumbs and scoped search never change the connected address. Every returned path is relative to the repository root, including when the address mounts a subdirectory. A skill opens with `?skill=marketing/skills/campaign/SKILL.md`; names are display text, not identifiers. The header of the page names the branch or ref the address follows, the commit, the path and the license, linked to the license file at the host when that is where the index found it, and marks a verified repository with a check in the accent.

When a folder has a README overview, its short introduction and a link to the original appear in the explorer, with or without a manifest. The link opens the existing file view; the page does not preload the full README or choose a translated source from the UI language. Overview-only files do not inflate search results or document counts.

Browse and search have continuation pages, including repositories with more skills than fit in the initial overview. The skill view renders each inherited manifest in order, appends context pages until complete, and shows required file contents. Supporting files remain accessible through folder browsing. Markdown resolves a leading slash from the repository root, rejects traversal outside it, and respects unavailable references reported by the REST API. The underlying tool contract is `browse_repo`, `search_repo`, `load_skill` and `read_repo_file` ([tools](../../docs/specs/tools.md)); the routes of the [REST API](../../docs/specs/rest.md) answer the same reads as JSON.

`dev/fixtures.ts` includes nested team groups, duplicate skill names and a folder with 230 skills. The development states page links to scoped searches and pagination. Server rendering receives `browse` or `find` alongside `mount` and seeds the same keys the browser requests in `src/api/keys.ts`.

## How it is built

`pnpm --filter @skillcdn/web run build` runs `skillcdn-web build` (`bin/skillcdn-web.mjs`), the command an installation runs, which does three things: the client bundle, with `licenses/npm.txt`, the notices of the npm packages it bundled (`dev/licenses.ts`); a self-contained bundle of `src/entry-server.tsx` that renders pages to HTML (`dist/render/entry-server.js`); and `scripts/prerender.mjs`, which writes into `dist/`:

- every static page once per language (`index.html`, `index.ko.html`, `explore/index.html`, ...), with its title, description, canonical and `hreflang` links, social-preview tags and structured data already in the HTML, because most crawlers do not run scripts;
- the documentation ([ADR-0049](../../docs/adr/0049-the-documentation-is-rendered-into-the-pages-from-the-repositorys-own-files.md)): `docs/index.html` and `docs/<slug>/index.html` per language, each listed in the sitemap in English alone (`alternates` in the manifest), the Markdown of each page as `docs/<slug>.md` with its links made absolute, and `llms-full.txt` with every page in it;
- a shell for pages that depend on data, for a host that cannot render them;
- `template.html`, the document that pages are rendered into, kept for the server;
- `llms.txt` per language;
- `routes.json`, which tells whatever serves `dist/` which file answers which URL in which language, and names the render module;
- `fonts/`, two unmodified faces of the pages' typeface, copied from the `pretendard` package, which the server sets the social previews of addresses in ([ADR-0032](../../docs/adr/0032-social-previews-are-drawn-by-the-server-for-each-address.md)).

The explorer view of an address is rendered by the server per request: it calls `renderAddressPage` from the render module with the language, the origin, the URL, what the deployment has (`features`: the sections of the front page and whether the search is there, which the server also writes into the head of every page for the browser to read, [ADR-0075](../../docs/adr/0075-a-search-across-the-packs-has-a-page-per-term-that-search-engines-may-list.md)) and the answers the page would ask the REST API for, and the page carries those answers in a JSON element (`#skillcdn-data`) so that the browser hydrates instead of loading them again (`src/api/initial-data.ts`, `src/api/use-resource.ts`). The page of a search term goes through `renderSearchPage` with the results the same way, and `renderSitePage` renders a page of the build per request where the deployment's features differ from what the build prerendered. The head of that page (`src/seo/head.ts`) says whether it may be indexed: the overview of an address without a ref and one skill are; a ref, a file, a search or an index that is not ready are not. The front page is rendered the same way, through `renderLandingPage` with the operator's showcase, empty or not; `renderLlmsTxt` takes the showcase too. Without a render module the prerendered page answers, and the browser asks `GET /api/v1/showcase` after it has mounted. A page of the deployment's own is rendered through `renderLegalPage` with its document, or with the absence of one, which the page shows as not found. The page of an account goes through `renderAddressPage` as well, with the first page of `GET /api/v1/owners/...`, and may be indexed once the account has something public to show; the pages of whoever is signed in and the consent page are rendered without data, as their frame. The page of an address names a card the server draws as its social preview (`/social/<address>?lang=..`, and `&skill=` for one skill); `socialCard` in [`src/social.ts`](src/social.ts) writes the card's words from the packs, and the server draws them ([ADR-0032](../../docs/adr/0032-social-previews-are-drawn-by-the-server-for-each-address.md)).

Languages share their paths; `?lang=ko` forces Korean on that page. A URL without a parameter is served in the language the request's `Accept-Language` asks for, else English, so a link preview is in the language of the app that fetches it ([ADR-0021](../../docs/adr/0021-a-url-without-a-language-is-served-in-the-language-asked-for.md)); the page served is that language's own, canonical URL included. In a browser such a URL is shown in the visitor's language, without the URL changing: when the visitor's choice differs from what the server sent, `public/boot.js` hides the page and the app renders it in that language ([ADR-0013](../../docs/adr/0013-language-decided-in-the-browser-without-changing-the-url.md)); otherwise the app hydrates what it got, which the root records with `data-lang`. Links inside the app carry no language, whatever page they are on ([ADR-0015](../../docs/adr/0015-a-forced-language-holds-for-one-page.md)), and a language the URL forces becomes the visitor's preference ([ADR-0017](../../docs/adr/0017-a-forced-language-becomes-the-preference.md)). Pages carry a placeholder instead of the public origin, which the server fills in, so one build works on any domain. For a plain static host, build with `SKILLCDN_PUBLIC_URL=https://your.host` and the origin is written into the files; such a host serves the default language only.

## Pages of an installation's own

An installation adds screens of its own to the pages without changing this workspace ([ADR-0099](../../docs/adr/0099-the-pages-take-pages-of-an-installations-own-from-a-configuration-of-the-build.md)): what its operator looks at, how its people have a pack made. A build is given a configuration, a file anywhere on the machine that exports `site`, which names the pages:

```tsx
import { defineSite } from "@skillcdn/web";
import { StatusPage } from "./status-page.js";

export const site = defineSite({
  pages: [
    {
      key: "status", // the address: /pages/status
      label: { en: "Status", ko: "상태" }, // one word, or a word by language
      menu: true, // named in the header's menu
      render: (context) => <StatusPage {...context} />,
    },
  ],
});
```

The published package builds it with `skillcdn-web build --config <file>` ([above](#build-it-with-pages-of-your-own)); a checkout of this repository at the release builds the same into `dist/`:

```
pnpm turbo run build --filter=@skillcdn/web^...
SKILLCDN_WEB_CONFIG=/srv/acme-ui/site.config.tsx pnpm --filter @skillcdn/web run build
```

[`examples/site`](examples/site/site.config.tsx) is a configuration with one page, which the tests render.

- **What a page is given** (`SitePageContext` in [`src/site-pages.ts`](src/site-pages.ts)): `client`, the REST API of the deployment as `@skillcdn/client` types it; `language` and `words`, the tag of the language shown and the product's words in it; `origin`; `search`, the query of the page's address, where a page keeps what it shows; and `navigation`, `go` and `replace`, which move to another page without loading a document. A page brings its own words, by language.
- **Where a page lives:** `/pages/<key>`, the same in every language; `sitePageHref(key)` names it. A key is lowercase letters, digits and hyphens, and a build fails on one that is not, or on a key twice.
- **A page is drawn in the browser alone.** The server answers its address with the frame, and `render` is called once the frame is up: never where pages are rendered to HTML, so a page may use `window` and storage as it likes, and is never a page for a search engine. A page that is to be found is a page of the product, added as the others are.
- **What a page may reach** is what the content security policy of the pages lets every page reach: scripts, styles and connections of the deployment's own origin. The admin API is there for a page that is given the operator's token; another service is reached where the installation's reverse proxy puts it under the same origin.
- **How it looks** is the tokens' to say (`var(--color-...)`, `var(--space-...)` of `src/styles/tokens.css`), in a CSS module beside the page, without inline styles.
- **What it imports:** `react`, `@skillcdn/client` and `@skillcdn/core` are resolved from the package wherever the file stands, so the installation's directory needs nothing else for them; `@skillcdn/web` is `src/site-pages.ts`, with its declarations in the package. What a page imports beyond them is the installation's own dependency, and the build lists it with the others in `licenses/npm.txt`. The development server takes the same configuration (`--config`, or `SKILLCDN_WEB_CONFIG` in `.env.local` or the environment of `pnpm --filter @skillcdn/web run dev`).
- **In a checkout, run the build of this workspace itself** (`pnpm --filter @skillcdn/web run build`), as above, once what it depends on is built: the task runner keeps the output of a build by what is in the repository, and a configuration is not.

## Adding a language

A pack in `src/i18n/messages/`, an entry in `src/i18n/languages.ts` and in `src/i18n/index.ts`, the code in the list in `public/boot.js`, and `public/og/og-<language>.png`. Tests fail until they all agree.

## Constraints

- **REST only.** The UI may import types, schemas and the address parser from `@skillcdn/core`, the REST API from `@skillcdn/client` and the files it serves from `@skillcdn/brand`, and nothing else from the workspace. Signing in and out are navigations to the server (`/auth/...`), never a request the UI makes with a credential of its own: the browser holds a session cookie scripts cannot read, and nothing else. The render module is the one thing the server calls, and it takes plain data.
- **Repository content is untrusted.** Markdown is rendered as React elements, never as HTML. Raw HTML stays text, and links go to `http(s)`, `mailto` or another file of the same mount. Pictures are shown ([ADR-0030](../../docs/adr/0030-pictures-in-repository-markdown-are-shown.md)): from their own `https` URL, or for a path of the repository from the host's raw copy at the commit the page shows, loaded lazily and without a referrer; anything else stands as its text. The picture that stands for a repository and its owner's picture arrive from the REST API as URLs and are shown the same way (`Picture` and `Avatar` in `components/ui.tsx`): decorative, without a referrer, and gone as a whole when the host does not serve them ([ADR-0031](../../docs/adr/0031-a-picture-for-a-repository-comes-from-its-manifest-or-the-operator.md)).
- **No inline scripts or styles**, so the pages work under a strict content security policy. The one exception is not in this workspace: the server may add an operator's tags to the head of every page (search-console verification, analytics, the deployment's own legal links; see `deploy/README.md`), and widens the policy for exactly those. Analytics ask first only where the visitor's region asks ([ADR-0051](../../docs/adr/0051-analytics-ask-first-only-where-the-visitors-region-asks-and-run-elsewhere.md)): the server's bootstrap leaves `window.skillcdnAnalytics` on the page and says whether this visitor is asked; where they are, the consent card (`components/consent-banner.tsx`) asks once and hands the answer back, and nothing loads before that; elsewhere analytics run at once and the footer offers to turn them off; a browser that signals Global Privacy Control never loads them. What the pages then send is below, under [Analytics](#analytics).
- **No secrets in the client.** Everything in a browser bundle is public.
- **What is one person's is not rendered for search engines or kept.** The page of a private repository, the account pages and the consent page say `noindex`; the page of a private repository names no social preview; and when a person signs out, a private repository on screen is asked for again as anyone would.
- **No business model in the UI**: no plans, prices or checkout (root `AGENTS.md`, rule 6).

## Analytics

What the pages send when a deployment has analytics and they may run ([ADR-0050](../../docs/adr/0050-the-pages-tell-analytics-only-what-is-public-and-usage-is-counted-in-the-database.md)). Everything goes through `src/analytics.ts`, the one module that talks to the script, and nothing leaves the page that is not public.

- **Whether they run** is decided per visitor ([ADR-0051](../../docs/adr/0051-analytics-ask-first-only-where-the-visitors-region-asks-and-run-elsewhere.md)): the server writes into each page, before the bootstrap, whether this visitor is asked first. In the regions the deployment asks (`ANALYTICS_CONSENT_REGIONS`, by default the European Economic Area, the United Kingdom and Switzerland), and whenever the visitor could not be placed, the card asks and nothing is loaded until they agree; elsewhere analytics run at once, and the footer's "Cookie settings" opens the same card (`components/consent-banner.tsx`) to turn them off, or on again; keeping or allowing them is the button, turning them off the quieter choice beside it. The words say cookies, not analytics, as a visitor expects them said. A browser that signals Global Privacy Control is never asked and never loads them. The answer is kept in `localStorage` (`skillcdn-consent`) for the next visit. The script's consent mode carries the same regions as its defaults, so a visitor the service itself places in one of them has analytics storage denied whatever the page was told.

- **Page views** are sent by the app, not by the script: `page_title` is the kind of page, and `page_location` a path that names only what is public. The page of a public repository is its address (`/gh/owner/repo[@ref][/path]`), with `view` (`overview`, `folder`, `search`, `skill`, `file`), `visibility`, and `skill` for a skill that loaded; a repository that is not public, or is nothing, is `/gh/-/-` with `visibility` or `outcome`; an account is its path, or `/gh/-`; the consent page is sent without its query; a bad address and a missing page are `/bad-address` and `/not-found`. Every view carries `site_language`. `page_referrer` is the page before, as it was sent, or the outside site the visitor came from; never a page of this origin.
- **Events**, each with parameters from a short list: `address_submit` (`kind`: `repository`, `owner`, `invalid`); `cta_click` (`id`: `hero_start`, `hero_search`, `console_start`, `steps_start` and `start`, the ways to the start page from the first screen, the console's bar, the steps and the last call, `hero_search` being the link beside the first; `featured_all`, `organizations_join`, `console_pack`, `console_open` where the deployment names a console, `builders_join`); `start_copy` (`step`: `skills`, `board`, `employee`, `team`; `what`: `address`, `command`, `sentence`; `client` for a command), what was copied on the start page; `search_submit` (`from`: `landing`, `start`, `explore`, `results`, each also as `<from>_chip` for a term offered under the box; `empty`), never with the term; `search_result_click` (`kind`: `skill`, `document`, `section`, `pack`; `pack`: what the pack is); `showcase_click` (`target`: `pack`); `connect_client` (`client`); `connect_start` (`client`, `method`: `install`, `open`, `copy_address`, `copy_config`, `copy_command`, `copy_shell`); `message_copy` (`client`); `sign_in_open` (`from`: `header`, `private`, `account`); `sign_in_start` (`from`: `dialog`, `consent`, `connect`); `login` (`method`: `gh`, sent by the page the tab comes back to signed in); `app_consent` (`approved`); `command_connect` (`approved`); `token_create`; `index_now` (`queued`). `client` is one of the connection guide's clients (`components/connect-clients.ts`).
- The funnel's key events are `connect_start`, `login`, `token_create` and `app_consent`. The property is set up to match, once: key events, a custom dimension per parameter, and its own measurement of page changes and of site search turned off, since the pages count their pages themselves and never send a search term ([`deploy/README.md`](../../deploy/README.md#the-analytics-property)).

## Rules

For whoever changes this workspace: read the root [`AGENTS.md`](../../AGENTS.md) first.

- **Keep the agreed direction.** The landing page leads with one promise and one action ([ADR-0129](../../docs/adr/0129-the-front-page-leads-with-one-action-and-a-start-page-says-how-to-begin.md)): hiring an AI employee, and the way to the start page, with the search across the packs as the quieter link beside it; then the agent accounts at work, real results of the reference pack, the console's board alive on the page, the packs with the search box, the ways to start, the builders; the brand's symbol and wordmark (the files of `@skillcdn/brand`: the symbol in its own blue, the wordmark white on the dark ground and black on a light one, never another colour), one blue accent for controls, links and states with one warm point colour reserved for badges, the hero mark and a builder's own case (`--color-point`, never a control), and panes of glass over the lit room of `tokens.css` (`glass.module.css` is the one pane; compose it, do not redraw it). Motion is scroll-driven where the browser can (`animation-timeline: view()`), off under reduced motion, and never on the main thread per frame: what plays by itself (the agent accounts' scene, the hand on the console's board, the steps the first time they are on screen) is `Element.animate`, and what follows the pointer (a card of the console's board) is a transform written on the element as the pointer moves. The one exception is the cloud of packs: once a visitor has taken hold of a pill it is a simulation that places the pills a frame at a time until every one is still, and never runs before that (`use-cloud-drag.ts`). Keep setup details off the front page: what a step takes is the start page's, and how it is done is the packs'. Larger changes of direction need a maintainer request.
- **An agent account is an employee in promotion.** The landing and the start page say "AI employee", and its like in every language pack, never "agent account", which is the word of the console and the documents; a test holds it. The scene and the words around it name no messenger and no other outside service, and show nobody's mark; it is a chat, whatever its window looks like.
- **Copy promises, it does not explain.** Landing copy is short, direct and in marketing register: a hook, then the fact. It leaves the how to the sections that show it; the promise is that someone who is not an expert runs a company with the AI they already use, said without saying so. Details belong in the FAQ, the connection guide and the docs, not in a hero line. The showcase shows real results only, made with the pack it names, never a mock-up.
- **The start page is a map.** `/start` says what each way to start takes, gives what to connect and the one sentence to tell an AI, and says in a line what the AI does once told ([ADR-0129](../../docs/adr/0129-the-front-page-leads-with-one-action-and-a-start-page-says-how-to-begin.md)); it explains nothing of how a step is done, which is the pack's to say to the agent that does it. Its ways are the front page's steps, in the same order and number, which a test holds. A sentence on it is said to a pack as that pack stands: before one changes, give it to an agent connected to the pack and read where it leads. What it says a step takes, and what the AI does then, is what the reference console's skills ask for and do, so it changes when they do.
- **A deployment chooses its front page.** The sections after the first screen are shown when the deployment's features name them (`src/features.ts`, written into the head by the server from `LANDING_SECTIONS`); the search box only where the search is there; and on the start page, the ways that need the console only where the front page shows the console or the agents. Render nothing that depends on them from anywhere but `useFeatures()`, so that the server and the browser render the same page.
- **Tokens only.** No raw color, font stack or pixel size in a component's CSS: add or reuse a token in `src/styles/tokens.css`. The social-preview card is the one exception, because it is a picture.
- **Connection illustrations.** Client marks and illustrated client windows retain their own brand colors inside the dark, blue-accented site. Keep every caption and screen label in the language packs. These are illustrative guides, never live connection status; keep their steps aligned with the official references in `connect-guide.md` of this workspace.
- **Fonts ship with the image.** The content security policy allows no foreign source, so a font is added as a package and imported in `entry-client.tsx`. Never link a font from a CDN. Only Hangul has a webfont, because only Hangul needs one: `styles/pretendard.css` is generated from the package and narrowed to the Hangul ranges, and Latin is drawn by the system fonts in `--font-sans`. Do not edit that file by hand. A font is a bundled dependency: its license must allow that (root `AGENTS.md`, Dependencies), and its notice ships in `public/licenses/`, listed in `THIRD-PARTY-NOTICES.md`.
- **Every word goes through the language packs.** No user-visible string in a component. English is the source of truth; keep `ko.ts` in step in the same change, in natural Korean. The development-only pages are the exception. Language packs are the one place where committed text is not English.
- **Copy says what exists.** No prices or plans, no comparisons with other products, no promises about features that are not built. Naming an MCP client we work with is fine.
- **Same paths in every language.** The `lang` query parameter forces a language and makes it the visitor's preference, as the switcher does; without it the server answers in the language `Accept-Language` asks for, else the default, and says `Vary: Accept-Language`; the browser shows the visitor's preference, else the browser's language, and the URL stays clean (ADR-0009, ADR-0013, ADR-0015, ADR-0017, ADR-0021). Links inside the app go through `Link`, which never carries the parameter, so a copied link opens in each reader's language. Never read a cookie on the server to pick a language, and never redirect to put the parameter in the URL.
- **Pages that should be found are rendered on the server.** A new static page is added to `STATIC_PAGES` in `src/entry-server.tsx` and gets a head in `src/seo/head.ts`; the view of an address is rendered per request through `renderAddressPage`. Whatever renders on the server must render the same in the browser: no `window`, `Date.now()` or storage during render; read them in effects. A page that loads data asks for it through `useResource` with a key from `src/api/keys.ts`, which is how the server's answers reach it.
- **Nobody is signed in on the server.** A page is rendered as one document for everyone: the session is `unknown` during server rendering and on the browser's first render, and becomes known in an effect (`auth/session.tsx`). Never render something of a person's from anything but `useSession()`, and never branch on it in a way that makes the first browser render differ from the server's. What a signed-in person gets goes into the account pages as a section (`ACCOUNT_SECTIONS`), not into a new top-level route.
- **One way out to sign in.** Only `components/sign-in.tsx` links to the route that leaves for the git host (`loginPath`); the development states page is the one exception. Everything else that offers signing in opens the sign-in dialog (`useSignInDialog()`), which lies over the page and comes back to it; there is no sign-in page (ADR-0043). The button never stands without the sentence under it that says what continuing agrees to, which is why the component shows nothing until the deployment's links are known (ADR-0041).
- **What an app says about itself is its word.** On the consent page and in the list of connected apps, a client's name and page are shown as text, marked as its own, and never linked or fetched; the host its answer goes to is the fact shown beside them.
- **The documentation is the repository's own files** (ADR-0049). What a page says is changed in `docs/`, never here; a file is published by listing it in `docs/nav.json`, and `dev/docs.ts` reads it when the pages are built; a file outside `docs/` is also re-included in the root `.dockerignore`, since the image builds the pages from its build context (a test in `dev/docs.test.ts` checks every listed file). A page is plain Markdown without front matter, and every relative link must lead to a file of the repository, with a fragment that names a heading of a published page: the build of a checkout fails on anything else, and says where (the image is built from a copy that has only the published files, so it resolves what it cannot see without checking, and the tests keep the check). A new section of `nav.json` needs its label in `docs.sections` of both language packs.
- **Repository content is hostile.** It reaches the DOM only through `components/markdown.tsx` or as text. Never `dangerouslySetInnerHTML`, never an `<iframe>`. A picture in repository Markdown is the one thing loaded from elsewhere (ADR-0030): an `https` URL as written, a path of the repository as the host's raw copy at the page's commit, always lazily and with `referrerPolicy="no-referrer"`; nothing else becomes an `<img>`.
- **No inline `style` attributes and no inline scripts**: the server sends a content security policy that forbids them.
- **Analytics learn nothing that is not public** (ADR-0050). Every page view and event goes through `src/analytics.ts`: a page is sent as what it is, an address only once the server has answered that the repository is public, and never a search, a typed path, a title or a sealed request. A new event is a name and a few parameters from a short list, written down in the README's "Analytics" section; nothing a visitor typed is ever a parameter.
- **An installation's pages come through the configuration, never into the product's routes** ([ADR-0099](../../docs/adr/0099-the-pages-take-pages-of-an-installations-own-from-a-configuration-of-the-build.md)). A screen that is one installation's is a page of `defineSite` (`src/site-pages.ts`), at `/pages/<key>`, drawn in the browser alone; the product's own build has none. What such a page is given is what `SitePageContext` says, and adding to it is adding to a contract installations build against: additive only.
- **This workspace is a published package** ([ADR-0101](../../docs/adr/0101-the-web-ui-is-published-as-a-package-that-builds-the-pages-with-an-installations-own.md)): installations build their pages from it with `skillcdn-web build` (`bin/`), outside this repository. What a build reads must be in `files` of `package.json`, and what it takes from the repository travels by `scripts/pack-files.mjs` (the documentation, the license, the trademark policy and the notices); never read a file of the repository outside this workspace from the build without carrying it the same way. A change here carries a changeset, like any published package's.
- **The REST API is the only backend.** Responses are parsed with the schemas from `@skillcdn/core`. When the contract changes, `dev/fixtures.ts` changes with it; `dev/fixture-api.test.ts` fails until it does.
- **New runtime dependencies need a reason** in the commit message, like everywhere else. The main bundle is what every visitor downloads: what only the explorer needs is loaded with it (`lazy` in `src/app.tsx`).

## Gotchas

- The integrated server caches the built web manifest and templates at startup. Restart it after rebuilding `WEB_ROOT`; otherwise it can reference removed asset hashes. Vite development previews reload changes automatically.
- A video only plays on some phones when the server answers byte ranges, which the integrated server does; a static host or a cache in front has to as well. A clip's poster is its first frame on purpose: with any other frame, playback starts with a visible jump.
- Muted autoplay is not guaranteed: Samsung Internet can be set to refuse it, and saver modes refuse it. A refused clip becomes the same clip as an animated image, never a control laid over it; under reduced motion the page does not ask, and the poster stands. A remote desktop session turns Windows animations off, so a browser there reports reduced motion: check that before calling a clip broken.
- `boot.js` may hide a page while the visitor's language is applied, but must preserve the server's `html.lang`, which says what the server sent. The client decides whether to hydrate from the root's `data-lang`, which no script before it touches, and `html.lang`, which must agree; only `applyHead` changes `html.lang` after rendering.
- Two ways a soft light grows a hard edge, both of which look like a blur that is not strong enough and are not. A radial gradient reaches its farthest corner by default, so in a box that is rounded or not square it is still opaque where the rounding cuts it: say `closest-side` when the fill must end where the box does. And a mask image is tiled and clipped to its own box, so putting one on a blurred element cuts the blur off at the box edge — which, on a glow, is an arc across the middle of it. Darken with a veil over the light instead of masking the light.
- A box with no fill of its own cannot keep a fixed hairline. `--color-border` is a colour, so the line is only as visible as the difference between it and whatever is behind it, and over the lights that difference goes to nothing exactly where the page is brightest — measured, the rules between the questions ran 1.00:1, the very colour of the ground they were drawn on. A line that has to hold over a varying ground is white let through (`--color-border-lit`), which lightens whatever is behind it and reads the same everywhere. Keep the fixed colours for a line on a surface.
- A decorative light behind a section is `z-index: -1` inside it, which puts it behind that section and in front of every section painted before it — and `isolation: isolate` on the section is what keeps it there. Pin such a light with `position: fixed` and it is still painted with its own section, so it lands wherever the window is over everything above it: that is how a section light comes to lie on the hero's title instead of behind it. Without the isolation it falls through to the page's own negative layer, behind all of the page's words; keep the isolation only on a section that has a surface of its own for the light to sit over. And the first section is a case apart, because a `view()` timeline's `cover` range opens a whole window before its subject arrives: the first section is already part-way through its pass on the first screen, so a fade that starts dark leaves that screen unlit and only one that starts lit can light it.
- An animation the stylesheet runs is the compositor's only on an HTML element. Measured in Chromium (158): `translate` and `rotate` animated on an `<svg>` element itself, and a place along a path (`offset-distance`), are recalculated on the main thread every frame, wherever on the page the element is and whether or not it is on screen: with six planets adrift, a page at rest recalculated style 660 times in four seconds on a 165 Hz screen, against 38 without them, and 55 once each motion stood on an HTML element around the drawing. To measure a page at rest, take the difference of `RecalcStyleCount` and `TaskDuration` of the DevTools protocol's `Performance.getMetrics` over a few seconds without scrolling, and without a `requestAnimationFrame` loop counting frames meanwhile: the loop forces a main frame every tick, and every running animation then recalculates style, composited or not. To find which animation it is, cancel them one at a time by `animationName` (`document.getAnimations()`).
- When a token suddenly does nothing, check that the comment above it closed. A stray `*/` in a declaration block makes the parser skip to the next `;`, which swallows the declaration under it; the token is then undefined, every `var()` on it is invalid at computed-value time, and the property falls back to its initial value with nothing said anywhere. It looks exactly like a value that has no effect.
- A custom property that holds `var()` references has them substituted where it is *written*, not where it is used: `--glass-surface` on `:root` carries the tint `:root` had, and an element that redefines `--glass-tint` on itself changes nothing about it. A variant of such a value is its own token, not an override of a part of it.
- A heading's `scroll-margin-top` is added to the document's `scroll-padding-top` (`base.css`), not laid over it: a fragment lands at the sum of the two. The document's own clears the header, so a page sets only what it puts under the header itself; measured on the documentation, 72 + 12 px put the heading 84 px down. The outline's mark reads the same two values, so it agrees with where a link lands.
- A small round box with a number in it centres nothing. The line the text sits on is as tall as the page's line height, which is taller than a box the size of one line; a box that cannot hold its line puts the line at the top rather than the middle, and the number lands at the foot of the ring. Say `line-height: 1` so it fits, and remember that a fixed height splits a padding between both sides, so an optical lift there costs twice the padding it does in a box that grows with its text.
- Replacing a CSS module file wholesale can leave the Vite development server serving it as an empty module: the stylesheet itself is right (ask for it with `?direct`), but the default export has no class names and every `styles.x` comes out `undefined`, so elements render with no class at all and no error anywhere. Touching the file again invalidates it. Editing in place does not trigger it.
- A function in a language pack whose key begins with `use` reads to the linter as a React hook, and calling it inside a condition fails the check (`useHookAtTopLevel`). Name such a key for what it says, not `useSomething`.
- Biome rewrites `import "./x.css"` to `./x.js` (`useImportExtensions`). Style sheets that are imported for their side effect carry a `biome-ignore` for that; CSS modules are not affected.
- Adjacent expressions in JSX (`{host}{path}`) become separate text nodes with a comment between them in prerendered HTML. Write one template string when the text must be searchable as a whole.
- `--font-mono` has no Hangul: Pretendard is declared for the Hangul ranges only and sits in `--font-sans`. A Korean line set in the code face therefore splits in two, the Latin in a monospace and the Hangul in whatever the system offers. Only set code in `--font-mono` (an address, a path, a call, a digit); prose stays in `--font-sans`, however technical it looks.
- There is one theme and it is dark: `tokens.css` sets `color-scheme: dark` and every color is a single value. Nothing reads or writes `data-theme`. Large address fields, where used, carry their own light-surface text colors (`--color-*-invert`).
- Text reads from the left. What is centered says so in its own rule and is nearly always a header: the landing hero, a section title and its lead, the head of a page, the short pages (not found, bad address) and the header bar. Two things that are not headers: the pair of buttons under the authors section is centered, and the footer is not centered at all — its two halves sit at the two ends of the page.
- Headless Chrome will not make a window narrower than about 500 px; to check a phone width, load the page in a 390 px wide iframe.
- The render bundle imports `pages/mount.tsx` statically while the client loads it lazily; the build warns that the dynamic import is ineffective in that bundle. It is meant to be.
- The fixture server's sign-in is one fact for the whole process, not a cookie: following `/auth/gh/login` signs the fixture person in for every browser that talks to it until it restarts or someone signs out.
- The server hydrates the page of an address only when `#skillcdn-data` is there and `data-prerendered` names the route; otherwise the browser renders afresh. A mismatch between what the server and the browser render shows up as a hydration warning in the console: check `useResource` gets the same answers on both sides.
