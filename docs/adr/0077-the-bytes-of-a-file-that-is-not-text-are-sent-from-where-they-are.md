# ADR-0077: The bytes of a file that is not text are sent from where they are, and never kept

- Status: Accepted
- Date: 2026-10-30
- Builds on [ADR-0033](0033-a-file-over-the-read-limit-is-named-with-its-source.md) (a refused read names the source) and [ADR-0076](0076-originals-travel-in-the-pack-and-the-repositorys-visibility-decides-who-reads-them.md) (originals travel in the pack). Supersedes the second sentence of point 4 of [ADR-0071](0071-a-deployment-serves-packs-from-a-directory-of-its-own.md) and its rejection of serving a directory pack's files as they are. The routes are in [specs/rest.md](../specs/rest.md#get-apiv1rawaddresspath) and the answers in [specs/tools.md](../specs/tools.md).

## Context

With originals and pictures in the pack (ADR-0076), the answer a read gives for a file that is not text has to lead somewhere, for every kind of pack. It did for one. A repository of GitHub got the raw URL of the file at the host. A pack served from a directory of the deployment got the page of the file in the explorer, which said that the file is not text and stopped. A directory served by the command had a `file:` URL on its mount, and gave it only for a file over the read limit: a picture under the limit ended in "the body is not available", since the command's reader had nothing to fetch a body with. A file kept in Git LFS was served as the pointer it is in the repository, by the tools and by the raw URL alike.

The deployment also paid for what it never used. A read of a file that is not text fetched its bytes from the host and stored them in `blobs` before saying that they are not text, and fetched them again at the next read, since a stored body that is not text reads as nothing. The first index of a commit downloaded the whole archive of the repository, originals included, once per round of bodies. A directory was read whole at every reread, pictures and originals hashed with the text, when the index wanted the text alone.

The maintainer decided that the server keeps no bytes of such files and serves none from a store: it gives a link that opens, and where it has the file on its own disk, it sends the file as it is. Nothing in this repository takes on the traffic of a git host's files.

## Decision

1. **A read of a file that is not text answers where the bytes are, and the deployment stores nothing of it.** A file whose name says that it is not text, a picture, an original, an archive, a program, is never fetched to learn that, unless it is small enough to be a Git LFS pointer. A file of another name is fetched once, from the host, to be read: text is stored as before; what is not text is not stored, and the reader remembers the hash so that it is not fetched again in that process. The files of a listed skill are stored whatever they are, since the skills extension serves their bytes (ADR-0025). The read limit stays where it is: a file over it is named with its source, as ADR-0033 says.
2. **Where the bytes are depends on where the pack is.** A repository of a git host: the host's raw URL, as before, for a public and a private repository alike; a file of a private repository is answered with one line more, that the host serves it only to a credential that may read the repository, since the URL names the repository and the host answers a browser session with nothing. A pack served from a directory of the deployment: the deployment's own route, `GET /api/v1/raw/<address>?path=`, which sends the file from the disk as an attachment, whatever its size, since the file is already where the deployment runs. A directory served by the command over HTTP: the same route on that server, and every result of that server names it. A directory served by the command over standard input and output, or read by one of its commands: the `file:` URL of the file on that machine, for every file that is not text, whatever its size.
3. **The route sends a served file as it is, and nothing runs.** It answers only a path the index lists and serves, under the license that governs it, resolved under the pack's directory through no symbolic link; it sends the bytes as `application/octet-stream`, as an attachment, with `X-Content-Type-Options: nosniff` and a Content-Security-Policy that allows nothing and sandboxes the document, so that HTML or SVG of a repository never runs on the deployment's origin: the headers GitHub's raw host sends for the same files. For a repository of a git host the route sends the reader on to the host's raw URL with a redirect, and carries no bytes.
4. **A Git LFS pointer is answered with where the host serves the file.** A file whose text is a pointer, by the specification's first line, is not readable here: the read says so, with the size the pointer names and GitHub's own raw route, `github.com/<owner>/<repo>/raw/<commit>/<path>`, which answers the file itself for a file kept in LFS and the raw host's bytes for any other. Where no host serves LFS, as in a directory, the pointer is the text it is.
5. **The index fetches the bodies it needs and no more.** Before the rounds, the indexer weighs, from the tree alone, fetching the bodies the store lacks in one archive against fetching them one by one, counting each request as a fixed cost in bytes of archive, and takes the archive once, before any round, only when it is not larger than that; a pack whose bytes are mostly originals is read file by file, and its originals are never downloaded. A directory is read with the tree only where the reading rules read text: a declaration, a document, a license; every other file is listed with a stand-in hash from its path, size and modification time, so that a changed file is a new tree, and is read from disk when something asks for its bytes.
6. **Slicing the indexing of words is deferred.** Word indexing runs in the `api` on first request, a bounded number at a time per process. With the bodies fetched as above the cost of a first index follows the text the limits admit, not the size of the repository; whether a long index should give its place up and come back in turns, as the embedding does, is decided when a measurement asks for it.

## Consequences

- Every read of a picture or an original ends in a link that opens: at the host, at the deployment's own route, or on the machine the command runs on. The explorer's page of such a file links there too.
- `blobs` holds text, and the files of listed skills; the bytes of a repository's pictures and originals are never in the database, and a deployment's storage follows what it serves as text.
- A pack that carries its originals costs its first index the text alone, and a directory pack costs a reread the text alone. Reading a file on disk again when its bytes are asked for is the price, paid by the few reads that ask.
- The route is one more place where a deployment sends bytes a repository author wrote, with the headers that keep a browser from treating them as a page of the deployment. It serves nothing a result does not already name.
- The raw URL of a private repository's file is as good as the credential that fetches it: the agent's, by the maintainer's decision, as the hint says.
- Rejected: a size limit on the route of a directory pack (the file is on the deployment's own disk, and the limit would turn a large original into a dead end); storing the bytes of pictures and originals in `blobs`, or in a blob store on object storage, to serve them (the deployment would carry what the host carries); proxying a git host's files through the deployment (the same); an MCP image content block for a picture under the limit (the link serves every client, a block only the ones that render pictures, and the server would read and send what it does not keep); a `file:` URL from a deployment (ADR-0071's reason stands: it names a path of the server's filesystem to a reader who cannot reach it).
