# ADR-0036: The deployment is the authorization server of its addresses, and authorization over MCP is optional

- Status: Accepted
- Date: 2026-10-04
- Builds on [ADR-0035](0035-people-sign-in-through-the-git-hosts-app.md). The contract is in [specs/permissions.md](../specs/permissions.md).

## Context

An MCP client reaches a private repository on a person's behalf, and the MCP specification says how a client gets a credential for a server: OAuth 2.1 with protected resource metadata, discovered from a challenge. Three things constrain how that is done here. An agent may never hold a token of the git host. A public address has to keep working for a client that knows nothing about authorization. And an anonymous client must not be able to tell a private repository from a name that is nothing, yet has to be able to start asking for access to the first.

## Decision

1. **The deployment issues its own tokens.** The `api` role is an OAuth 2.1 authorization server for the addresses it serves: authorization codes with PKCE and nothing else, tokens that are random strings stored as hashes in PostgreSQL. No identity service stands beside the image.
2. **A token is optional.** Without one, what is public is served as before. A request without a token for anything else gets a `401` with a challenge that names the address's metadata, whether the name is a private repository or nothing at all. With a valid token, what its person cannot see is the usual `404`. A token that is no good gets the same `401`, marked as such, except at a public address, which needs none and serves the request.
3. **A public address shows no sign of signing in.** It never answers `401`, it has no protected resource metadata, and the authorization server's own metadata is not at the root of the origin: the issuer is `<origin>/oauth`, with its metadata where an issuer with a path has it. Clients differ in how they decide that a server wants a sign-in. Some wait for a `401`; others look for these documents before they connect, from the server's URL up to the root, and start signing in when they find one. Either kind finds nothing at a public address, and everything at one that asks.
4. **The resource is the address.** An address that asks for a credential has protected resource metadata at its own well-known path, a client names the address as its `resource`, and a token is good at exactly that canonical address, ref and path included.
5. **Clients identify themselves, and a person decides.** A client is a metadata document at an `https` URL, or a dynamic registration open to anyone. Neither is vouched for; the consent page shows the name as the client's own word and who its answer goes to as the fact: a host on the web, or the scheme of an app's own link, never a host such a link only writes after itself. Redirect URIs are `https`, this computer, or an app's own scheme, and are matched exactly.
6. **Asking stores nothing, and sends nobody anywhere.** An authorization request is sealed and carried through the consent page; rows are written only when a person agrees. A request that is wrong is shown on that page and never answered with a redirect to the client: registration is open, so the endpoint would otherwise forward a browser wherever anyone liked. The page that asks is a page of the web UI, which is why signing in needs it. It asks only a person who can open the address: for anyone else, and for a name that is nothing, there is nothing to allow, and the client is told no.
7. **Refresh tokens rotate.** A refresh token presented long after its first use revokes its grant; presented within a short grace it gets a pair of its own, for clients that retry or share a store.
8. **A token says who agreed, not what they may see.** Every request checks the person's access with the git host, so taking access away at the host needs no revocation here.

## Consequences

- Self-hosted and hosted deployments authorize the same way, from one image and one database.
- Turning signing in on changes nothing for whoever uses public repositories, in any client: there is nothing new for a client to find at their addresses.
- Whether an address has metadata is one lookup of its name per request for the document, the same lookup a request to the address makes. The metadata of an issuer with a path is looked for in more than one place. It is served where RFC 8414 puts it and under the issuer itself, where clients that append to it look; the places that would hold an OpenID Connect document stay empty, because this is not an OpenID provider.
- A person allows an app once per address. A token for a repository's root is not good for a sub-path or a ref of it, so mounting several addresses of one repository asks several times; in return a token's reach is exactly what the person read on the consent page.
- Anyone can add a row to the clients table by registering. Requests are bounded in size, clients nobody has used are bounded in number and removed after a while, and what a person can make (grants, and token pairs per grant) is bounded too. Limiting requests per client stays with whatever is in front of the server.
- A name that is nothing is taken through signing in like a private repository, so that nobody learns which it is by trying names; only then, to the person who signed in, does the page say that the address cannot be opened, without saying why. The connection fails there rather than later: an app is never left connected to something that answers not-found to every call. Someone who adds the git host's app to a repository afterwards looks again on the same page, or connects again.
- A client that sends a wrong request gets no error at its redirect URI, as the base protocol would have it; its person reads what was wrong on the consent page, with the protocol's error code for whoever builds the client.
- Reading a client's metadata document is the one request the server makes to a URL somebody else chose. It goes to public addresses over TLS only, without redirects, for a small body and a short time.
- Rejected: handing the agent the git host's token, or proxying the host's own authorization (the first rule above); signed self-contained access tokens (they cannot be taken back, and every request reads the database for the permission answer anyway); a token per repository (the resource a client knows is the URL it connects to, and clients do not agree on prefix rules); a `404` for an anonymous request to a private repository (a client could then never begin to ask for access); requiring a token everywhere (public repositories need nobody's permission); the origin as the issuer, with its metadata at the root (a client that looks for a way to sign in before it connects then signs in at every address, public ones included, and one such client is among those the connection guide covers); metadata for every address (the same, one step earlier); a `401` for a token that is no good at a public address (it would point at metadata the address does not have, for a credential the address does not need); letting a person allow an app for an address they cannot open, to work once they can (the app then looks connected and finds nothing, and its person is not told why).
