# ADR-0059: The command connects with a code a person approves, and receives a repository token it never shows

- Status: Accepted
- Date: 2026-10-18
- Builds on [ADR-0040](0040-a-token-for-an-agent-reads-one-repository-as-its-maker.md) and [ADR-0056](0056-the-rest-api-has-a-client-and-the-command-reads-a-deployment-through-it.md), whose rejection of a sign-in of the command's own this supersedes. The contract is in [specs/permissions.md](../specs/permissions.md#a-command-connects-with-a-code) and [specs/rest.md](../specs/rest.md#people).

## Context

The `skillcdn` command reads a private pack with a repository token ([ADR-0040](0040-a-token-for-an-agent-reads-one-repository-as-its-maker.md)) that a person made on their account page and gave it through standard input ([ADR-0056](0056-the-rest-api-has-a-client-and-the-command-reads-a-deployment-through-it.md)). That is a secret shown on a screen, carried through a clipboard or a file, and often through a chat with the agent that runs the command; the account page did not even say how the command takes it. A person who is not a developer should not have to see a token at all: they should tell their agent to connect, and say yes once, on the deployment's own pages, as the person the command will read as. The reference console reached the same conclusion for its own command and connects it with a short code a person approves; the command here is used by the same people in the same chats, and the connection guide of a repository is to offer the command beside the MCP clients, which it cannot while connecting it means pasting a secret.

An access token of the authorization server ([ADR-0036](0036-the-deployment-is-the-authorization-server-of-its-addresses.md)) would not do: it is good at one canonical address, ref and path included, while a command bound to a repository reads its tags and folders too, and it would need a registered client and a refresh token kept beside it. The token the command needs is the repository token it already takes.

## Decision

1. **The command asks to connect, as nobody.** `skillcdn login --url <origin> <address>` sends the deployment the repository it wants and what the command calls itself and where it runs (`POST /api/v1/connect`) and gets back three things: a code for a person to read, eight letters from an alphabet without look-alikes in two groups of four; the deployment's own page for that code; and a secret of its own, shown nowhere, with which it claims the token. The request lasts ten minutes, and a deployment holds a bounded number of them at once. Nothing is asked about the repository here: a request is anyone's, and whether the name is a private repository or nothing is for the person who approves to learn. The command prints the page and the code, and an agent running the command relays them to its person.
2. **A person approves on the deployment's own pages, signed in.** The page for the code (`/connect/<code>`) says what asks to connect, which repository it will read and that it will read as the person; the person checks that the page shows the code their command showed, names the token and says for how long it is good, as the token form does, and approves, or says that it is not theirs. Only a private repository the person can open right now is approved, as only such a repository gets a token from the form: anything else is refused where the person can read why, and a public repository ends the request, since the command reads it without any of this. Approving and declining come from the deployment's own pages, with the session, never with a token.
3. **The token is made when the command claims it, and handed over once.** The command asks every few seconds with its secret (`POST /api/v1/connect/claim`) and is told to wait, or is given the token. Nothing secret rests in the database meanwhile: the request holds the hash of the command's secret, the code, the repository, what the command calls itself, and once approved who approved, the name and the lifetime. On the claim the repository is resolved for the approver once more, as their own request would be, the token is made for them as the account page makes one, the request goes, and the secret of the token is answered to the command, which keeps it where `login --token-stdin` always kept it. A request that expired, was declined or was claimed already is not found, whatever is asked of it; a git host that cannot be asked leaves the approval for the next claim.
4. **The command keeps a token per deployment and repository.** A repository token is good at one repository, so the credentials file keeps logins by origin and repository, and a read presents the token kept for the repository it reads, else the one kept for the origin alone, which a token given through standard input without a repository is. `logins` names the repositories, never the tokens.
5. **The paste stays for jobs.** `skillcdn login --url <origin> --token-stdin` still takes a token from standard input, for a job or a hook that holds one; at a terminal it asks for the token without echoing it. The account page shows the command beside the other ways to give a token out, and says how a command connects without one.

## Consequences

- A person never sees a token unless they ask for one by hand; an agent never shows one; the clipboard and the chat carry a code that is good for ten minutes and for nothing but saying yes.
- Whoever approves a code gives a command they may not be looking at their own standing for one repository, which is the point and the risk: the page says so plainly, names what asks and shows the code to compare; the code expires soon, and a request is answered once.
- The token a command receives is a repository token like any other: listed on the account page under the name the person gave it, removed there, expiring, and reading as its maker, so the git host still decides what it opens ([ADR-0040](0040-a-token-for-an-agent-reads-one-repository-as-its-maker.md)).
- A new table, `connect_requests`, swept with the sessions and the tokens; four routes under `/api/v1/connect`; `@skillcdn/client` gains their functions, and the pages gain `/connect` and `/connect/<code>`.
- Rejected: a device-code grant at the authorization server (an address-bound access token with a refresh token, where the command needs the repository token it already takes; the standard shape can still be added for clients that speak it); the token made at approval and stored until claimed, which puts a secret at rest for the whole wait; the code typed into the terminal instead of the token, which still has a person type at a terminal; a long-lived code, which widens the window in which a code shown to the wrong person is approved.
