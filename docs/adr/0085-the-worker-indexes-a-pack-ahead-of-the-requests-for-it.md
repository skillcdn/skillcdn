# ADR-0085: The worker indexes a pack ahead of the requests for it

- Status: Accepted
- Date: 2026-11-11
- Builds on [ADR-0007](0007-snapshot-rows-coordinate-indexing.md) (the snapshot row of a commit decides who indexes it), [ADR-0038](0038-the-git-hosts-events-end-what-is-remembered.md) (an event of the git host establishes nothing), [ADR-0064](0064-meaning-search-runs-on-pgvector-and-pg-boss-behind-an-embedder-port.md) (the worker and its queue), [ADR-0068](0068-a-mount-serves-the-last-indexed-commit-while-the-newest-is-not-ready.md) (what answers while a commit is indexed), [ADR-0071](0071-a-deployment-serves-packs-from-a-directory-of-its-own.md) (packs from a directory) and [ADR-0072](0072-the-worker-embeds-the-packs-first-and-the-rest-when-asked.md) (the ranks of repositories).

## Context

A commit is indexed when a request asks for it. A push the git host announces makes the refs of its repository due, and the request after it finds the new commit, starts its index and is answered from the commit before: nobody waits, and everyone reads the commit before until some request has paid for the new one. A pack of the deployment's own directory is read again only when a request finds its ref's time up, and a pack copied into the directory is unknown, to the search across packs as well, until somebody asks for it by name. A change of the reading rules sends every index back to be rebuilt by the next request for it. The worker runs the queue and indexed only what somebody designated.

The item was scheduled for 0.5.0 with the questions this record answers: what starts an index ahead of a request, for which repositories, and within which bounds.

## Decision

1. **The worker asks the host where a ref points, and indexes the commit, ahead of requests.** Every minute a pass of the worker lists the repositories with a ref that is due and queues one job for each. The job asks the host where the remembered moving refs of the repository point, the ten asked of it last, exactly as a request would, indexes a commit that has no index under the reading rules in force, and queues its sections for embedding as a commit `api` indexed is queued. Only a ref somebody asked for is remembered, so nothing is indexed that no request ever named, the packs of point 4 apart.
2. **A ref is due when the host announced a push, when its time is up, or when its commit has no index.** An event still establishes nothing: a push makes the refs of its repository due, as before, and notes on them that it was announced; the note says where to look, and ends when the host is next asked where the ref points, by a request or by the worker. A ref's time is up when the host was not asked about it for `INDEX_AHEAD_MINUTES`. And a commit has no index when it was never built, was sent back for a rebuild by a change of the rules, was handed back by a process that stopped, or failed and is due for the retry its snapshot schedules.
3. **Which repositories are looked at is the deployment's choice, and a repository that is no pack is never among them.** `INDEX_AHEAD` is `listed`, the default: the packs of the deployment's directory and the repositories the operator lists are looked at when their time is up or their commit has no index. `packs` adds every repository that is a pack, as the embedding ranks them: one that holds a manifest or a skill, and one that is not public. `none` turns the indexing ahead off. A push the host announced is followed for every pack under both settings: the host announces only where its app is installed, which the owner of the repository did. A repository with neither a manifest nor a skill is indexed by the requests for it, as before.
4. **The packs of the directory are found, not waited for.** The pass lists the deployment's directory and queues the packs it has never seen, resolved as anyone would resolve them, so that an installation's packs are indexed, and searched across, once they are copied in.
5. **The work is bounded where it starts.** One job per repository waits and one runs, so the pushes of a burst are one look; the jobs have a queue of their own, run one at a time, beside the designated indexing, which keeps its own; a pass queues at most `INDEX_AHEAD_LIMIT` repositories, the announced first, then by rank, then the longest unasked; a host that limits its answers or gives none is left alone for the time it names, five minutes at least, and so is a repository the deployment refuses to serve; a ref the host says is gone is forgotten. The `Entitlements` port decides whether a repository is served, as for a request.
6. **Nothing changes for a reader, and nothing depends on the worker.** `api` indexes on request as before, where no worker runs and where a request comes first; the snapshot row coordinates the two. The `api` role needs no queue for this: what an event leaves is a note in the database, and the worker reads it.

## Consequences

- With a worker and the host's events, a push is served within about a minute and the time its index takes, whoever asks first; without the events, a listed repository within `INDEX_AHEAD_MINUTES`.
- A change of the reading rules is rebuilt by the worker for the repositories of the scope, by rank and at the pass's limit a minute, while each is served from its index under the rules before (ADR-0068). The requests rebuild the rest, as before.
- Looking costs one question to the host per ref per interval. Under `listed` that is what the operator chose; under `packs` on a public deployment it is every pack, which wants the deployment's token (`GITHUB_TOKEN`): the anonymous allowance of a git host is spent by a few dozen refs.
- An installation with no git host copies a pack into its directory and finds it indexed, embedded and searched across within a minute or two, with nobody connecting first.
- `repo_refs` gains a column for the note, and a ref the host says is gone leaves the table. A pack whose directory was removed stops being looked at the same way.
- Indexes still accumulate, and faster where every push is indexed: each commit a ref passed through keeps its index until a rule for which are kept is decided, which is a decision of its own.
- Rejected: indexing the commit an event names (it would write down what a delivery says); `api` queueing a job when an event arrives (it would need the queue on a deployment without the search by meaning, and a deployment without a worker would only collect the jobs); indexing every repository the deployment knows (anyone makes a deployment know any public repository by asking for it once); an action of its own on the `Entitlements` port (no implementation tells the two apart yet; the decision to serve applies).
