# ADR-0070: A deployment is searched across every pack it serves

- Status: Accepted
- Date: 2026-10-23
- Builds on [ADR-0063](0063-packs-of-documents-are-served-to-agents-through-structure-words-and-meaning.md) (words and meaning), [ADR-0064](0064-meaning-search-runs-on-pgvector-and-pg-boss-behind-an-embedder-port.md) (point 2, the exact search over one mount, and an approximate index when a search across repositories asks for one), [ADR-0068](0068-a-mount-serves-the-last-indexed-commit-while-the-newest-is-not-ready.md) (the commit a mount is served from) and [ADR-0069](0069-a-word-of-a-query-weighs-by-its-rarity-among-the-entries-searched.md) (the weighing of words); refines what [ADR-0028](0028-the-front-page-and-the-explorer-are-operator-content.md) and the REST specification say of listing what is indexed.

## Context

Everything an agent gets from a deployment is one pack at a time: it connects to an address and searches, browses and reads inside it. Which pack to connect to it has to know beforehand, from a person, a page or a list. The explorer shows what the operator features and nothing else, by a decision taken when nobody wanted a catalog: asking for an address does not opt its author into one. A deployment that indexes hundreds of packs, public ones at that, knows the answer to "which pack says anything about this" and cannot be asked.

Phase C of the document-pack work named the explorer's search and the search across repositories as what remained. The maintainer decided that the search covers everything the deployment serves, not a list the operator keeps, with performance watched; that it is offered to agents as the other tools are, over MCP and over REST; and that the pages gain a search box later, built on the same route.

## Decision

1. **A deployment is searched across every public pack it serves.** The search covers every public repository that has an index, at the snapshot a mount of its default branch is served from (ADR-0068), and nothing private, blocked by the operator, or without an index yet. A repository stays out of it with `search: { hub: false }` in its root manifest; it is then found at its own address alone. A search answers a question; it lists nothing: a result names a pack because something in it matched, with the match, and no route enumerates the packs, so the sentence of the REST specification stands with that refinement.
2. **It is one more surface of the same kind.** The root of the deployment is an MCP server with one tool, `search_packs`, whose results name every item under the address of its pack and tell the model to connect there for the four tools; `GET /api/v1/search` answers the same as data, and `@skillcdn/client` reads it. A browser's `GET /` stays the landing page: the MCP transport posts, deletes, and gets a stream it asks for by name.
3. **It ranks as a search inside a mount does.** The words of the query, read with the default rules since the packs differ in language, weigh by their rarity across all the packs (ADR-0069) and match over all their entries at once, through the one full-text index; where the deployment searches by meaning, the sections nearest the query over all the packs' vectors are fused with the words' results by reciprocal rank fusion, and the first results are reranked where a reranker is configured. A result is a skill by its name and description or a document with the sections that matched, read from its body where the license lets the deployment pass it on (ADR-0026).
4. **It is bounded in time, by configuration.** Every statement over the packs runs under a timeout of its own (`HUB_SEARCH_TIMEOUT_MS`, two seconds unless set), after which the database cancels it; the words running out of time is an answer of its own, the meaning running out leaves the words to answer, as inside a mount. How many entries the words and the meaning each bring to the fusion is `HUB_SEARCH_CANDIDATES`; `HUB_SEARCH=false` leaves the route and the server out. A deployment on its own machine sets these as it likes.
5. **The vectors are searched exactly, until a measurement asks for more.** The search over the sections of every pack is the exact comparison of ADR-0064, bounded by the timeout; the approximate index that decision reserved for a search across repositories is added when a deployment's packs make the exact one miss its time, as an index per model on the same table and the same query, and the measurement after the release decides.

## Consequences

- An agent, or a person, that does not know which pack holds something asks the deployment once and connects to the pack named. The pages' search box, when it comes, is the same route rendered.
- The explorer's list stays the operator's, and no route lists what is indexed; what the search reveals of a public pack is what a search of that pack reveals, and an author who wants less writes `search: { hub: false }`.
- A search across packs costs one count and one match over every pack's entries, and one comparison over every pack's section vectors where meaning is on, each bounded; the packs themselves are read once in a while, not per search.
- Nothing is counted for a pack found this way until it is connected to: the search is the deployment's, not any pack's.
- Rejected: searching the operator's featured list alone (the maintainer, 2026-10-23: the search box would lose its point); an MCP tool per pack that reads through the root (the agent would never need the pack's own address, and the four tools would carry an address parameter each: the pack is the unit this service is built on); a catalog route beside the search (what was decided against when the explorer was made, and still is); an approximate index from the start (nothing measured asks for it yet).
