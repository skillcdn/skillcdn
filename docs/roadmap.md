# Roadmap

What exists, what is being built, what comes next. Update this file in the same change that starts, finishes or drops an item. Detailed task tracking happens in GitHub issues; this file stays coarse.

## Done

- **Foundation.** Monorepo layout, pinned toolchain, lint, typecheck and test pipeline, CI, container image with role dispatch, license, contributor and agent documentation.
- **Milestone 1: serve a public repository end to end.** An MCP client connects to `/gh/<owner>/<repo>` for a public GitHub repository and can discover, load and read skills and documents: address and skill-repo parsers in `core`, the GitHub adapter, the first schema with full-text search, the `api` and `migrate` roles with lazy indexing, test-only repository fixtures, an end-to-end test with the MCP client SDK, and what the server needs to run behind a reverse proxy. Publishing and deployment are not part of this repository ([ADR-0008](adr/0008-repository-ends-at-an-image-that-builds.md)); the milestone is really over with the first hosted staging deployment.

- **Milestone 2: the web UI.** A person opens the service in a browser, understands what it does in their language, pastes an address and sees what an agent gets from it: REST API v1 ([specs/rest.md](specs/rest.md)); the landing page and the explorer in English and Korean, prerendered per language with metadata, structured data, social-preview images and `llms.txt` ([ADR-0009](adr/0009-web-ui-prerendered-per-language.md)), with the design decided with the maintainers (an approachable creative landing page, one blue accent, layered dark surfaces, and the brand's symbol); the server serves the build, renders the page of an address with its data so that it can be indexed, and generates `sitemap.xml` and `robots.txt` ([ADR-0011](adr/0011-address-pages-rendered-on-the-server.md)); the UI runs on its own for whoever designs it, from fixtures or against a running server; usage statistics per public repository and skill, and distinct clients counted without identifying one ([ADR-0010](adr/0010-distinct-clients-by-daily-keyed-hash.md)); search-console and analytics tags from configuration. Login and repository connection arrived with private repositories, in milestone 5.
- **Milestone 3: MCP in depth.** An agent that connects to an address knows what it got and uses it well, whatever the client, and a person who opens the page of a repository connects their agent from there. Skills travel through the MCP skills extension `io.modelcontextprotocol/skills` from the same index and publication policy as the four tools, which remain for discovery and for clients without the extension ([ADR-0024](adr/0024-skills-travel-through-the-mcp-skills-extension.md)); a skill on the wire is assembled from its sources ([ADR-0025](adr/0025-a-skill-on-the-wire-is-assembled-from-its-sources.md)); content is addressed by repository-root paths, with folder browsing, scoped search and skills loaded in pages ([ADR-0022](adr/0022-repository-paths-and-progressive-skill-loading.md), [ADR-0023](adr/0023-optional-introductions-and-explicit-publication.md)); a tool result is the one text written for the model ([ADR-0034](adr/0034-a-tool-result-is-the-text-written-for-the-model.md)); a file over the read limit is named with its source ([ADR-0033](adr/0033-a-file-over-the-read-limit-is-named-with-its-source.md)); a skill may include a shared page of the repository, which travels with it on every route ([ADR-0044](adr/0044-a-skill-may-include-a-page-of-a-shared-document-set.md)); the repository manifest gives names, descriptions, rules, document roots and translations ([ADR-0018](adr/0018-skillcdn-fields-in-skill-md-under-one-key.md)), the `check` role reports what the indexer reads ([ADR-0020](adr/0020-a-check-role-reads-a-working-tree-with-the-indexer.md)), and results carry a provenance notice until somebody vouches for the repository ([ADR-0019](adr/0019-the-operator-vouches-for-repositories-until-owners-can.md)). The page of a repository leads with the steps to connect it to the common clients ([guide contract](specs/connect-guide.md)), the landing page and the explorer lead with what can be made, and a URL without a language is answered in the language asked for ([ADR-0021](adr/0021-a-url-without-a-language-is-served-in-the-language-asked-for.md)). The server survives hostile repository content and mixed-version deployments. An address serves only what is its repository's own ([ADR-0039](adr/0039-an-address-serves-only-what-is-the-repositorys-own.md)), and the server bounds its own work for requests from nobody: request and index size limits, bounded indexing per process, and a short memory of names that are nothing, shared between processes ([permissions](specs/permissions.md#what-is-served-to-whom)); limiting requests per client is the job of whatever sits in front. The extension passed the MCP Inspector's conformance checks, and the maintainers connected the real clients by hand, to a local server and to the hosted service. Nothing in this repository can test that, so it is done again after every change to what a client sees and whenever the protocol changes.
- **Milestone 4: ready for public operation.** A deployment that serves other people's repositories can say what it does with their content, honor their licenses, take content down, and show its visitors what it must; nothing in it is specific to one operator, and every switch has an off default that suits a private installation. The license a skill carries decides whether its body is served or only described with a link to its source, and the operator keeps verified, featured and blocked lists through a token-protected admin API, with a purge that removes what was indexed of a repository ([ADR-0026](adr/0026-serving-follows-the-license-and-the-operators-lists.md)). The legal surface is off until it is configured: links to terms and privacy pages and a contact for content reports, pages the operator can write into the deployment in every language it has ([ADR-0029](adr/0029-terms-and-privacy-pages-can-be-written-into-the-deployment.md)), analytics only after consent, and a checklist for public deployments in the deploy documentation. The license, notice and trademark files travel in the image, the web build carries the licenses of its bundled packages, and `pnpm check` refuses a production dependency under a license outside the allowlist. Distinct clients are counted under a key derived from a configured secret and the day ([ADR-0027](adr/0027-client-hashes-are-keyed-from-a-configured-secret-and-the-day.md)). The front page leads with a showcase the operator writes, with its media stored in the database and served by hash, and the explorer keeps its own featured list; a fresh deployment shows the reference repository on both ([ADR-0028](adr/0028-the-front-page-and-the-explorer-are-operator-content.md)). A repository declares its picture in its manifest, or the operator gives an address one ([ADR-0031](adr/0031-a-picture-for-a-repository-comes-from-its-manifest-or-the-operator.md)), and the page of an address unfurls with a card the server draws for it ([ADR-0032](adr/0032-social-previews-are-drawn-by-the-server-for-each-address.md)).

## Now: milestone 5, people and private repositories

Goal: a person signs in with their git host and uses a private repository from the pages and from their AI app, with the host deciding who sees what; an account has a page of its own. The contract is [specs/permissions.md](specs/permissions.md).

- [x] Signing in through a GitHub App ([ADR-0035](adr/0035-people-sign-in-through-the-git-hosts-app.md)): sessions, the person's token encrypted at rest and used only to ask, private repositories read and indexed through the installation, the host's answer cached briefly and failing closed, resolution that keeps a private repository and a name that is nothing indistinguishable.
- [x] Authorization over MCP, optional ([ADR-0036](adr/0036-the-deployment-is-the-authorization-server-of-its-addresses.md)): the deployment as OAuth 2.1 authorization server of its addresses, with protected resource metadata, client metadata documents and dynamic registration, PKCE, tokens bound to one address, refresh rotation, and a consent page that asks only a person who can open the address. A public address shows no sign of it: no challenge, no metadata of its own, and none at the root of the origin, since the issuer has a path.
- [x] The web UI for it: a sign-in dialog that every way to sign in opens over the page a person is on, with one button for the git host and the deployment's terms and privacy policy under it ([ADR-0041](adr/0041-a-sign-in-begins-on-a-page-of-the-deployments-own.md), [ADR-0043](adr/0043-a-sign-in-begins-in-a-dialog-over-the-page.md)), every sign-in past the git host's account picker ([ADR-0042](adr/0042-every-sign-in-passes-the-git-hosts-account-picker.md)), the account menu in the header, account pages built from a registry of sections (overview, private repositories, connected apps), the consent page, the private mark and the sign-in steps in the connection guide of a private repository.
- [x] The page of an account at `/gh/<owner>` ([ADR-0037](adr/0037-an-account-has-a-page-made-from-what-the-git-host-shows-everyone.md)): its public repositories as the host lists them, the indexed ones with skills first, for any account, without indexing on listing; rendered on the server and open to search engines.
- [x] The git host's events ([ADR-0038](adr/0038-the-git-hosts-events-end-what-is-remembered.md)): deliveries of the app's webhook, verified and then only ever ending what is remembered. A push makes the refs due, so the next request indexes the new commit; a repository made private or deleted closes at once; a removed installation takes the index of what was not public with it; a revoked authorization signs the person out; changes of collaborators, teams and members end the answers about who can see what, where the app may read members. The lifetimes remain the bound for what the host does not announce.
- [x] Tokens for agents with nobody to sign in ([ADR-0040](adr/0040-a-token-for-an-agent-reads-one-repository-as-its-maker.md)), planned as project tokens: a person makes one on their account pages for a repository they can open; it reads every ref and path of that repository over MCP, as its maker, so the git host still decides what it opens; it expires, is removed by its maker, and goes when the host stops vouching for them. The account pages have a section for them, and the connection guide of a private repository points at it.
- [ ] Try it by hand against a real GitHub App and the clients of the connection guide. The recorded fixtures cover the adapter, and the documents the clients publish about themselves are in the tests; what each client shows when it signs in can only be seen in the client. To look at in particular: that every client finds the metadata of an issuer that has a path, that a public address is added without any sign-in by the clients that look for one before they connect, that the deliveries of the app's webhook arrive and are accepted, that a terminal client reads a private repository with a token, and that every sign-in shows the git host's account picker, on a first sign-in before the host's own approval page.

## After milestone 5

1. User documentation: how to write a skill repository and how to use one from an agent. Written for repository authors and the people who use their repositories, not as a description of internals. One source: every topic lives in exactly one Markdown file in this repository, the published documentation is rendered from those files, and everything else links to them instead of repeating them. How it is published is decided when the work starts. The format a repository follows is an authoring convention on top of the Agent Skills layout, specified in [specs/skill-repo.md](specs/skill-repo.md); on the wire a skill is a plain Agent Skills skill. `skillcdn/skills` is the reference repository, the one the explorer offers to try, and will carry a skill that writes a repository in the format.
2. Packages on npm, under the `@skillcdn` scope. The first candidate is the `check` command, so that the author of a repository sees what an agent would get from it without the image; which packages there are is decided when the work starts. To settle with it: what a package is called and does, how its versions relate to the server's, and how it is published, since no workflow of this repository logs in to a registry ([ADR-0008](adr/0008-repository-ends-at-an-image-that-builds.md)).
3. `worker` role: indexing ahead of requests, when a push arrives and on a schedule, with a rule for which commits' indexes are kept. Until then a push only makes the refs due, and the next request indexes.
4. Self-hosted compose bundle, with a published image for self-hosters; GitLab and Gitea adapters, with the address grammar for nested namespaces decided before the address spec becomes normative, and signing in through those hosts.
5. `intake`, and composed tools declared in Markdown or YAML; `run` is defined against the rule that repository code never executes.
6. What a signed-in person gets beyond private repositories. The account pages take a new section per feature; nothing is decided about which.

## Later, undecided

Rankings fed by the usage statistics, next to the operator's featured list. Embedding search, and a search that understands inflected languages (a Korean query finds nothing in a Korean repository unless the words are written the same). A command-line client. A work-board module for parallel agents. Signed-commit verification for publishers. Aliases for verified publishers. Distribution through a small plugin that points at an address, and import by hosts that snapshot a server's skills when a plugin is submitted.
